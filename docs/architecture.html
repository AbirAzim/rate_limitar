Where every request goes

Which layer limits what

Each layer stops a different kind of traffic, and the cheaper the layer, the earlier it runs. The thresholds get tighter the closer a request gets to your code.

LayerLimits byExample ruleKnows your users?
WAF IP, country, bot score, attack patterns Block an IP above 100 req/s; block SQL injection payloads No
API gateway IP, API key, route 20 req/s per IP; 10,000 req/day per API key Partly: API keys
Your app (this repo) IP today; user, plan or action later 3 req/s per IP; 5 login attempts per account per 15 min Yes

Client IP through the chain. With the CDN, gateway and load balancer in front, the connection your app sees always comes from the load balancer. The real user IP travels in X-Forwarded-For, so TRUST_PROXY must equal the number of proxies in front of the app (3 here), or the app should read the edge's own header (Cloudflare sends CF-Connecting-IP). The app servers should also accept connections only from the load balancer, so nobody can skip the edge and forge that header.

How the breaker decides

Database: replication is built into MongoDB

An Atlas cluster is never one database server. Even the free tier is a replica set: three copies of the same data, each in a different availability zone (a separate datacenter in the same region). MongoDB copies every write from the primary to the secondaries itself, so you don't write any replication code and don't need a queue for it.

QuestionAnswer
Another load balancer for the DB? No. The MongoDB driver inside each app is topology-aware: it gets the list of nodes from the mongodb+srv:// connection string, watches which one is primary, sends writes there, and switches automatically after a failover.
A queue to copy writes? No. The oplog is the replication log, and the secondaries pull from it themselves.
When would a queue help? For work that doesn't have to happen inside the request: sending emails, absorbing a burst of writes, calling slow third parties. That's a separate design choice, not replication.
Can the 3 servers read from secondaries? Yes, with read preference secondaryPreferred. It spreads read load, but a read can be a few milliseconds behind the latest write. Keep the default primary for anything that must see the user's own just-written data.

When the primary dies

App settingValueWhy
Connection string mongodb+srv://… Lists every node via DNS, so the driver can find a new primary itself
retryWrites true (default) A write cut off by a failover is retried once on the new primary
Write concern w majority (default) Acknowledged writes are on 2 of 3 nodes and survive a failover
Read preference primary, or secondaryPreferred for read-heavy routes Trade always-fresh reads for spreading load
serverSelectionTimeoutMS e.g. 15000 How long a request waits for a primary before failing; keep it below your HTTP timeout

Beyond one replica set. To survive a whole region going down, Atlas can place the nodes in two or three regions instead of three zones. To grow past what one primary can write, Atlas shards the data across several replica sets and runs routers (mongos) in front of them; the driver talks to the routers. Neither is needed at this size.

rate_limitar · architecture v4 · Blog service, one login

A second service, one login: the blog joins over GraphQL

The blog runs as its own service on AWS AppSync, next to the REST API, and reads and writes its own database in the same MongoDB cluster. Users sign in once with Amazon Cognito, and the same token works on the REST API and the blog; no service keeps its own passwords.

Builds on v3. Everything not shown here is unchanged: the edge and layered limits, the REST rate limiter and breaker, and MongoDB replication and failover.

New since v3
  • Amazon Cognito user pool: one sign-in, one token for REST and GraphQL
  • Blog service on AWS AppSync with Lambda resolvers
  • Separate blog database and DB user in the same Atlas cluster
  • GraphQL schema, resolver map and design decisions
  • Failure rows for Cognito, AppSync and the shared connection limit

Two services side by side

One login for every service

Cognito is the only place that knows passwords. It hands the client a signed token (JWT) containing the user's id (sub), email and groups. Every service checks the token's signature against Cognito's public keys, which they download once and cache, so checking a token never calls Cognito and adds no network hop.

WhereHow it checks the token
API gateway (REST)JWT authorizer pointed at the Cognito user pool; rejects bad tokens before they reach your servers
Express app (this repo)Verifies again with aws-jwt-verify (keys cached in memory) and puts req.user = { sub, email, groups } on the request
AppSyncCognito user pool auth mode, built in. Resolvers receive identity.sub and identity.groups
Video service (later)Same user pool, same token; nothing new to log into

With a real user id on every request, the app's rate limiter can key on sub instead of IP for signed-in users, so one user can't dodge the limit by switching networks and a shared office IP doesn't throttle everyone behind it.

The blog service

The blog is its own service with its own code, deploys and database, even though it shares the Atlas cluster for now. AppSync owns the GraphQL schema, auth and subscriptions; small Lambda functions hold the logic and talk to MongoDB.

Resolvers Lambda with the MongoDB driver AppSync has no built-in MongoDB data source (it has DynamoDB, Lambda, HTTP, OpenSearch, RDS), and Atlas's own Data API has been retired

New ways things can fail

FailsAppWhat happens
Cognito degraded New sign-ins and token refreshes fail. Tokens already issued keep working until they expire (up to 1 h), because services verify them with cached keys.
AppSync or blog Lambdas degraded The blog is down; the REST API is unaffected, and the reverse is also true. Separate services fail separately.
Atlas connection limit degraded A Lambda spike opening too many connections can starve the REST API too, since they share the cluster. Capped with maxPoolSize and reserved concurrency.

rate_limitar · architecture v5 · Team stacks, blog media

Two teams, two stacks: the blog gets its own Valkey and S3 for images

The REST team and the blog team each own their own cache, their own database and their own deploys. Blog images live in S3 and reach readers through CloudFront, so neither MongoDB nor Valkey ever holds image bytes, and cached posts stay small.

Builds on v4. Unchanged: one Cognito login, AppSync with Lambda resolvers, the REST path and rate limiter, and MongoDB replication.

New since v4
  • Ownership split: REST team and blog team stacks, shared login, edge and cluster
  • Valkey "blog" for post cache, per-user limits and view counters
  • S3 blog-media with direct uploads through signed URLs, and an image processor
  • What's cached, how big it gets, and the eviction policy
  • Failure rows for each Valkey, the image processor and media delivery

Who owns what

How an image gets into a post

Image bytes never pass through AppSync or Lambda. AppSync requests are capped at a few megabytes and Lambda payloads at 6 MB, and pushing files through them costs time and money. Instead the Lambda hands the browser a short-lived, single-purpose upload link, and the browser sends the file straight to S3.

S3 settingValueWhy
Public accessBlockedOnly CloudFront (OAC) can read, only signed links can write
uploads/ lifecycleDelete after 1 dayOriginals from abandoned drafts don't pile up
media/ keysContent-hashed namesNever overwritten, so they can be cached with max-age=31536000, immutable
Processor failures2 retries, then a dead-letter queueA bad file doesn't block the rest; failures can be inspected and replayed
Post deletedDelete its media/{postId}/ prefixNo orphaned images

What goes in Valkey "blog"

Because images live in S3, a cached post is only its text and metadata: a few kilobytes to a few tens of kilobytes, even for long posts. Values are compressed before storing, and anything above about 100 KB is better not cached at all, since large values slow every read of them.

KeyHoldsTypical sizeLifetime
cache:post:{id}Post text, title, tags, image keys (compressed JSON)5–30 KB10 min; deleted when the post is edited
cache:posts:latest:{page}Summaries for the feed: title, excerpt, thumbnail key~5 KB60 s
ratelimit:{sub}:…Per-user limits for GraphQL, same Lua scripts as RESTbytesOne window
counter:views:{id}View count, INCR per readbytesNo expiry; flushed to MongoDB every minute

Eviction policy volatile-lru. When memory fills, Valkey only evicts keys that have an expiry, oldest-used first. Cached posts go first and simply reload from MongoDB; view counters have no expiry, so they are never dropped before they're saved. Size the node so eviction is rare; the smallest node with a replica, or ElastiCache Serverless, is enough to start.

New ways things can fail

FailsAppWhat happens
Valkey "blog" degraded Blog reads fall through to MongoDB (slower, more load); per-user GraphQL limits fall back to the WAF's per-IP rule. The REST API doesn't notice.
Valkey "rest" degraded Only the REST API is affected, as in v1–v4. The blog doesn't notice.
Image processor degraded New images wait in uploads/; retries and the dead-letter queue catch up once it's fixed. Existing images and all text keep working.
S3 or CloudFront media degraded Posts load without images. Images already cached at the edge or in browsers still show.
