Two teams, two stacks: the blog gets its own Valkey and S3 for images

The REST team and the blog team each own their own cache, their own database and their own deploys. Blog images live in S3 and reach readers through CloudFront, so neither MongoDB nor Valkey ever holds image bytes, and cached posts stay small.

Builds on v4. Unchanged: one Cognito login, AppSync with Lambda resolvers, the REST path and rate limiter, and MongoDB replication.

Who owns what

How an image gets into a post

Image bytes never pass through AppSync or Lambda. AppSync requests are capped at a few megabytes and Lambda payloads at 6 MB, and pushing files through them costs time and money. Instead the Lambda hands the browser a short-lived, single-purpose upload link, and the browser sends the file straight to S3.

S3 settingValueWhy
Public accessBlockedOnly CloudFront (OAC) can read, only signed links can write
uploads/ lifecycleDelete after 1 dayOriginals from abandoned drafts don't pile up
media/ keysContent-hashed namesNever overwritten, so they can be cached with max-age=31536000, immutable
Processor failures2 retries, then a dead-letter queueA bad file doesn't block the rest; failures can be inspected and replayed
Post deletedDelete its media/{postId}/ prefixNo orphaned images

What goes in Valkey "blog"

Because images live in S3, a cached post is only its text and metadata: a few kilobytes to a few tens of kilobytes, even for long posts. Values are compressed before storing, and anything above about 100 KB is better not cached at all, since large values slow every read of them.

KeyHoldsTypical sizeLifetime
cache:post:{id}Post text, title, tags, image keys (compressed JSON)5–30 KB10 min; deleted when the post is edited
cache:posts:latest:{page}Summaries for the feed: title, excerpt, thumbnail key~5 KB60 s
ratelimit:{sub}:…Per-user limits for GraphQL, same Lua scripts as RESTbytesOne window
counter:views:{id}View count, INCR per readbytesNo expiry; flushed to MongoDB every minute

Eviction policy volatile-lru. When memory fills, Valkey only evicts keys that have an expiry, oldest-used first. Cached posts go first and simply reload from MongoDB; view counters have no expiry, so they are never dropped before they're saved. Size the node so eviction is rare; the smallest node with a replica, or ElastiCache Serverless, is enough to start.

New ways things can fail

FailsAppWhat happens
Valkey "blog" degraded Blog reads fall through to MongoDB (slower, more load); per-user GraphQL limits fall back to the WAF's per-IP rule. The REST API doesn't notice.
Valkey "rest" degraded Only the REST API is affected, as in v1–v4. The blog doesn't notice.
Image processor degraded New images wait in uploads/; retries and the dead-letter queue catch up once it's fixed. Existing images and all text keep working.
S3 or CloudFront media degraded Posts load without images. Images already cached at the edge or in browsers still show.
