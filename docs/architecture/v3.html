From the edge to the database: every layer a request crosses

Traffic is filtered three times before it reaches your code: the CDN and WAF at the edge, then the API gateway, then the load balancer. Server A stays an app-only primary with double weight, and the database is a three-node replica set, so no single machine can take the API down. Everything drawn dashed is a rented managed service, so none of it uses your servers' RAM.

Where every request goes

Which layer limits what

Each layer stops a different kind of traffic, and the cheaper the layer, the earlier it runs. The thresholds get tighter the closer a request gets to your code.

LayerLimits byExample ruleKnows your users?
WAF IP, country, bot score, attack patterns Block an IP above 100 req/s; block SQL injection payloads No
API gateway IP, API key, route 20 req/s per IP; 10,000 req/day per API key Partly: API keys
Your app (this repo) IP today; user, plan or action later 3 req/s per IP; 5 login attempts per account per 15 min Yes

Client IP through the chain. With the CDN, gateway and load balancer in front, the connection your app sees always comes from the load balancer. The real user IP travels in X-Forwarded-For, so TRUST_PROXY must equal the number of proxies in front of the app (3 here), or the app should read the edge's own header (Cloudflare sends CF-Connecting-IP). The app servers should also accept connections only from the load balancer, so nobody can skip the edge and forge that header.

How the breaker decides

Database: replication is built into MongoDB

An Atlas cluster is never one database server. Even the free tier is a replica set: three copies of the same data, each in a different availability zone (a separate datacenter in the same region). MongoDB copies every write from the primary to the secondaries itself, so you don't write any replication code and don't need a queue for it.

QuestionAnswer
Another load balancer for the DB? No. The MongoDB driver inside each app is topology-aware: it gets the list of nodes from the mongodb+srv:// connection string, watches which one is primary, sends writes there, and switches automatically after a failover.
A queue to copy writes? No. The oplog is the replication log, and the secondaries pull from it themselves.
When would a queue help? For work that doesn't have to happen inside the request: sending emails, absorbing a burst of writes, calling slow third parties. That's a separate design choice, not replication.
Can the 3 servers read from secondaries? Yes, with read preference secondaryPreferred. It spreads read load, but a read can be a few milliseconds behind the latest write. Keep the default primary for anything that must see the user's own just-written data.

When the primary dies

App settingValueWhy
Connection string mongodb+srv://… Lists every node via DNS, so the driver can find a new primary itself
retryWrites true (default) A write cut off by a failover is retried once on the new primary
Write concern w majority (default) Acknowledged writes are on 2 of 3 nodes and survive a failover
Read preference primary, or secondaryPreferred for read-heavy routes Trade always-fresh reads for spreading load
serverSelectionTimeoutMS e.g. 15000 How long a request waits for a primary before failing; keep it below your HTTP timeout

Beyond one replica set. To survive a whole region going down, Atlas can place the nodes in two or three regions instead of three zones. To grow past what one primary can write, Atlas shards the data across several replica sets and runs routers (mongos) in front of them; the driver talks to the routers. Neither is needed at this size.

If one piece fails

FailsAppWhat happens
Server A up Load balancer sees /health fail and sends all traffic to B and C. Slower, not down.
Server B or C up Same: the other two keep serving.
Valkey primary up Provider promotes the replica in seconds. Meanwhile requests are allowed (today) or limited per server (with the breaker).
All of Valkey degraded API keeps working. App rate limits are off (today) or per server, up to 3× (with the breaker). WAF and gateway limits still apply. Cache misses go to MongoDB.
MongoDB primary up A secondary is elected primary in about 12 s. The driver holds writes and retries them once, so users see a slow request, not an error. Cached reads still come from Valkey.
MongoDB secondary up No visible effect. Atlas replaces the node, and it copies the data back from the others.
One CDN, gateway or LB machine up Each is run on many machines by the provider; a failed one is replaced without you noticing.
A whole CDN, gateway or LB service down Every request passes through all three, so a provider-wide outage of any of them makes the API unreachable. Rare, but these are the layers you can't route around without a second provider.
Whole provider region down Surviving it needs a second region with DNS failover, usually not worth it at this size.
